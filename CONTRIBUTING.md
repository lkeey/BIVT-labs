# Как вносить изменения

В репозитории изменения проходят через pull request. Не отправляйте учебные
работы прямо в `main`.

## Перед началом

1. Для новой задачи обновите сведения о ветках: `git fetch origin`.
2. Создайте отдельную ветку от актуального `origin/main`, например:

   ```bash
   git switch -c codex/03sql-coursework-docs origin/main
   ```

   Если для задачи уже создана отдельная ветка или worktree, продолжайте в ней;
   не пересоздавайте ветку и не сбрасывайте чужие изменения.
3. Применяйте `AGENTS.md` затрагиваемого проекта. Читайте его README для нужных
   команд и устройства проекта. Держите изменение в границах дисциплины.

## Подготовка изменения

- Добавляйте в staging только файлы, относящиеся к задаче. Проверьте
  `git status --short` и `git diff --cached --check` перед коммитом.
- Проверьте изменённое поведение командами из README проекта. Для правок только
  документации сверьте ссылки, имена и команды с файлами проекта. В pull request
  укажите реально выполненные проверки и причину пропуска нужных проверок.
- Не включайте секреты, локальные настройки, файлы сборки, кэши и личные
  материалы. Используйте `.env.example` для безопасных примеров настроек.
- Обновите README или другой документ проекта, если меняются его структура,
  требования или команды запуска.

## Pull request

1. Просмотрите весь diff относительно `origin/main`; убедитесь, что в нём нет
   изменений других дисциплин и локальных файлов.
2. Отправьте ветку в origin и откройте pull request в `main`.
3. Заполните [шаблон pull request](.github/PULL_REQUEST_TEMPLATE.md): укажите
   затронутые проекты, краткое описание, проверки и документацию.
4. Дождитесь проверок и review. После устранения замечаний обновите ту же ветку;
   объединяйте pull request согласно принятым в репозитории проверкам.

## Область ответственности

Каталоги `01Py/`, `02C#/`, `03SQL/`, `03SQL-CourseWork/` и
`03TechnologiesOfProgramming/` — отдельные проекты. Обычно один pull request
меняет один такой проект. Общие файлы корня, `.github/`, `.githooks/` и
`scripts/` можно менять, когда задача требует единого поведения для
репозитория; объясните необходимость в описании pull request.
