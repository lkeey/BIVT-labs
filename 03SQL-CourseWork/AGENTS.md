# Правила для курсовой по SQL Server

Этот каталог — отдельный проект курсовой на SQL Server 2025 и T-SQL. В
`database/postgres/` находится параллельная PostgreSQL-реализация для
публичной демонстрации; она не заменяет T-SQL и SQL Graph в курсовой. Не
смешивай эти скрипты с лабораторными из `03SQL/`, где используются SQL Server
2019 и PostgreSQL 16.

Карта компонентов: `database/` — каноническая модель и процедуры; `api/` —
OpenAPI-контракт; `backend/` — Go HTTP API и Firebase Auth; `worker/` — Python
OCR/индексация и сервис query embeddings; `web/` — статический JavaScript-сайт;
`docs/` — архитектура, ER-диаграммы, развёртывание и план записки;
`compose.yaml` — локальная сборка прикладных сервисов; `tools/` — проверка
контракта. Начинай с README нужного компонента или документа рядом с задачей.

- Для состава проекта и принятой архитектуры смотри `README.md` и
  `docs/architecture.md`; открывай только те разделы, которые относятся к задаче.
- Каноническую схему, SQL Graph, начальные данные и запросы храни в
  упорядоченных T-SQL-файлах `database/`. Поддерживай синтаксис SQL Server
  2025. PostgreSQL-эквиваленты помещай только в `database/postgres/` и
  документируй отличия без изменения предметных правил, ACL и API-контракта.
- HTTP-контракт меняй в `api/openapi.yaml` вместе с затронутой SQL-операцией.
  `x-implementation-status: planned` означает, что серверный маршрут ещё не
  реализован; `unavailable` — маршрут отвечает 503 до подключения зависимости.
  Сверяй `implemented` с реально зарегистрированными Go-маршрутами.
- SQL Server отвечает за реляционные данные, SQL Graph, текстовые фрагменты и
  выборку с проверкой доступа. Не выбирай embedding-модель и размер вектора без
  решения в документации проекта. OCR, создание embeddings и генерация ответа
  LLM выполняются на внешнем прикладном уровне; не представляй их как встроенные
  возможности T-SQL.
- Сохраняй связь извлечённых сущностей и рёбер с исходным материалом и его
  координатами. Поиск и рекомендации должны сначала учитывать доступность
  источников пользователю.
- Держи ревизию embedding-модели одинаковой в SQL `EmbeddingModel`, worker и
  сервисе запроса; смена модели требует переиндексации. Firebase UID и
  `@UserID` связывает только доверенный backend после проверки ID token.
- Для проверки изменяющих данные запросов используй транзакцию с `ROLLBACK`.
  Инициализационные скрипты, предназначенные для постоянного применения,
  оставляй повторяемыми и явно документируй их порядок.
- Для повторяемого процесса работы с моделью смотри repo-local Skill
  `../.agents/skills/sql-coursework/SKILL.md`.
