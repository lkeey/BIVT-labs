# API-контракт курсовой

[`openapi.yaml`](openapi.yaml) — проект **HTTP API v1**, а не работающий сервер.
Контракт не привязан к Kotlin, Go или Python. Возможный JavaScript-сайт на
Firebase Hosting общается только с backend по HTTPS; SQL Server и ключи LLM
доступны лишь backend и фоновому обработчику.

## Как читать контракт

- Идентификаторы SQL `bigint` передаются строками: JavaScript `Number` не
  представляет весь диапазон `bigint` точно. Время — UTC в RFC 3339.
- `401` означает отсутствие сессии; `403` — запрет на действие известному
  пользователю; `404` объединяет отсутствие объекта и отсутствие права его
  видеть, чтобы не раскрывать закрытые материалы. В сообщениях об ошибках нет
  SQL-текста или текста недоступного источника.
- Повторное создание сообщества с тем же `slug` и определением или повторная
  заявка на членство возвращает `200` с существующим объектом; новая запись —
  `201`. Backend должен отличить эти исходы при преобразовании результата SQL.
- Закрытые сообщества скрыты в списке и карточке для посторонних. Владелец
  может передать ссылку с `communityId` вне API: по этому ID пользователь
  подаёт заявку `PENDING`; содержимое сообщества остаётся недоступным до
  одобрения. Владелец или администратор видит ожидающие заявки через
  `GET /v1/communities/{communityId}/memberships`. В v1 нет токенов приглашения
  и передачи владения; владелец не может выйти из сообщества.
- `POST` документа принимает JSON с текстом или multipart с PDF/DOCX. Лимит
  исходного содержимого — **10 MiB в байтах**, как в `DocumentVersion` и
  `knowledge.usp_SaveDocumentVersion`; тип и сигнатуру файла проверяет сервер.
  Ответ `202` возвращает ID для опроса `GET /v1/documents/{documentId}`. Автор
  видит состояние `PROCESSING` или `FAILED`; оригинал PDF/DOCX скачивается
  только после `READY` через проверяющую ACL процедуру
  `knowledge.usp_GetDocumentFile`.
- `POST /v1/rag/queries` возвращает `202`; `GET` показывает статус. `COMPLETED`
  требует хотя бы одну цитату из реально использованных, текущих и доступных
  фрагментов. `NO_SOURCES` возвращает короткое сообщение без вызова LLM.
  `assistant.usp_GetRagTurn` различает ожидающий ход, отсутствие источников и
  отзыв доступа; одного пустого результата `vAnswerWithCitations` для этого
  недостаточно. Если доступ к любому использованному источнику отозван после
  ответа, `GET` возвращает `410` без сохранённого текста ответа и цитат.
- Лента возвращает только доступные опубликованные посты и документы; причины
  берутся из текущей фильтрованной выдачи, а не из старого кеша.
- Реакцию можно поставить на доступный пост, комментарий или готовый документ.
  Автор скрывает свой пост или комментарий с проверкой вида материала в SQL;
  владелец, администратор и модератор сообщества могут скрыть материал через
  `PUT /v1/content/{contentId}/moderation/hide`.

## Соответствие T-SQL

| API | T-SQL-операции | Нужно для HTTP-реализации |
| --- | --- | --- |
| Посты, комментарии и модерация | `social.usp_PublishContent`, `social.vAccessibleContent`, `assistant.usp_RevokeContentAccess` с `@ExpectedKind`, `social.usp_ModerateContent` | Серверное чтение, пагинация, преобразование ошибок SQL |
| Документы | `knowledge.usp_SaveDocumentVersion`, `knowledge.usp_GetDocumentFile`, `ops.IndexOutbox` | Приём файла, DTO и статус, OCR/embedding worker; не давать API прямой `SELECT` на `FileBytes` |
| RAG | `assistant.usp_StartRagSession`, `usp_StartRagTurn`, `usp_SearchRag`, `usp_RecordRetrievedChunks`, `usp_SaveRagAnswer`, `usp_SaveRagNoSources`, `usp_GetRagTurn`, `vAnswerWithCitations` | Embeddings, LLM, повторные ACL-проверки перед генерацией и авторизованная HTTP-выдача |
| Лента | `assistant.usp_GenerateRecommendations`, `vRecommendationFeed` | Авторизованная выдача и формат ответа |
| Сообщества, членство, подписки, реакции | `social.usp_CreateCommunity`, `usp_RequestMembership`, `usp_SetMembership`, `usp_LeaveCommunity`, `usp_SetFollow`, `usp_SetReaction`, `usp_ListPendingMemberships` | Авторизованная HTTP-выдача, DTO и пагинация |
| Сессии | `auth.UserAccount`, `auth.UserProfile` | Проверка внешнего OIDC-токена, связь с локальным UserID, хранение/отзыв серверных сессий; миграция схемы |

`x-sql-operation` и `x-sql-operations` в OpenAPI указывают SQL-объекты,
**не готовые HTTP endpoints**. `x-implementation-status: planned` у каждого
маршрута явно обозначает недостающий прикладной код. Клиент никогда не задаёт `UserID`
для SQL-процедур: backend берёт его только из проверенной сессии. Роль SQL
пользователя backend следует ограничить разрешёнными процедурами и
представлениями, не предоставляя прямой доступ к таблицам. Запланированные
чтения профилей, публикаций и метаданных документов потребуют ACL-проверяющих
SQL-операций или представлений до выдачи ограниченной роли backend.

## Сессия и браузер

Контракт предусматривает обмен проверенного OIDC identity token на короткую
серверную сессию. Конкретный провайдер пока не выбран; Firebase Auth можно
подключить без изменения ресурсов API. Сервер проверяет подпись, `issuer`,
`audience`, срок действия и привязку внешней личности к `auth.UserAccount`.
Публичная регистрация, восстановление пароля, продление сессии и передача
владения сообществом пока **не входят** в API и потребуют отдельного решения.

Для сайта на другом origin backend должен разрешить только заданный origin по
CORS и HTTPS, ограничивать частоту запросов и размер тела до чтения файла.
Если выбран bearer token, браузер хранит его в памяти, не в `localStorage`.
Если frontend и API будут доступны через один origin, можно использовать
`HttpOnly; Secure; SameSite` cookie с защитой изменяющих запросов от CSRF.

## Порядок реализации

1. Реализовать серверную идентичность и закрыть прямые права на таблицы;
   подключить готовые транзакционные SQL-операции к маршрутам API.
2. Реализовать DTO и ACL чтения материалов с курсорной пагинацией. Автору
   разрешить видеть состояние обработки своего документа.
3. Подключить очередь OCR/embeddings, затем RAG orchestration с проверкой
   источников до и после генерации, и ленту по существующей T-SQL-процедуре.
4. После выбора Kotlin или Go поднять backend, а JavaScript frontend разместить
   на Firebase Hosting. Адреса серверов, секреты и SQL-учётные данные задавать
   через конфигурацию среды, не добавлять в репозиторий.
