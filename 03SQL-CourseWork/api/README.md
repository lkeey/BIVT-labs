# HTTP API курсовой

[`openapi.yaml`](openapi.yaml) описывает Go backend из [`backend/`](../backend/README.md).
Базовый путь — `/api/v1`. Все маршруты приложения требуют
`Authorization: Bearer <Firebase ID token>`; исключения `/healthz` и `/readyz`
описаны в README backend. Браузер не подключается к SQL Server.

## Личность и доступ

Go API проверяет Firebase ID token через Admin SDK на каждом запросе, включая
срок действия, проект и отзыв. Затем `auth.usp_GetOrCreateFirebaseUser`
сопоставляет проверенный UID с SQL-пользователем. Внешний email не объединяет
аккаунты. Параметр `UserID` в SQL-процедуры передаёт только backend; числовой
ID в URL обозначает целевой объект, а не личность вызывающего.

SQL-логин API должен состоять в роли `coursework_api`. Она даёт `EXECUTE` на
разрешённые процедуры без прямого доступа к таблицам. Закрытые сообщества
скрыты от посторонних; заявка `PENDING` не даёт доступа. Владелец может
передать ID сообщества вне API для подачи заявки. После блокировки пользователя
доступ закрывается даже к открытому сообществу.

## Формат

- SQL `bigint` передаётся строкой, чтобы JavaScript не терял точность.
- Время передаётся в UTC по RFC 3339. Страницы содержат `items` и
  `nextCursor`; курсор непрозрачен для клиента.
- `400` означает некорректный ввод, `401` — недействительный Firebase token,
  `403` — запрет операции, `404` объединяет отсутствие объекта и отсутствие
  права его видеть, `409` — конфликт состояния. Текст SQL-ошибки клиенту
  не показывается.
- Новый объект возвращает `201`; повтор с тем же определением/заявкой может
  вернуть `200`. T-SQL возвращает флаг `Created` для этих случаев.

## Маршруты

| Область | Реализация |
| --- | --- |
| Профиль и сообщества | Проверяемые SQL-чтения и процедуры создания, членства и модерации. |
| Посты и комментарии | Публикация, текущие редакции, редактирование, скрытие, подписки и реакции. |
| Документы | Текст или PDF/DOCX до 10 МиБ, хранение оригинала в SQL, проверяемое скачивание готовой версии, статус обработки для автора. |
| Лента | `assistant.usp_GenerateRecommendations`; выдача повторно фильтруется по текущим правам. |
| RAG | `POST /rag/queries` строит embedding, ищет доступные источники и записывает ответ с проверенными цитатами; `GET /rag/queries/{queryId}` повторно проверяет источники. Без настроенных моделей POST возвращает `503`. |

У документа `POST` возвращает `202` и ID. После отдельной обработки outbox
статус меняется с `PROCESSING` на `READY` или `FAILED`. Для текстового документа
`GET /documents/{documentId}/file` выдаёт `text/plain`; для PDF/DOCX — оригинал
после проверки ACL. Исторические версии не скачиваются через v1.

RAG-маршрут завершает обработку до ответа HTTP и возвращает `201` с `queryId`
и `Location`: состояние уже `COMPLETED` или `NO_SOURCES`. Если сервис
embeddings или модель ответа недоступны, новый ход не создаётся. Ответ LLM
обязан ссылаться на номера источников `[1]`…`[5]`; в SQL записываются только
действительно упомянутые цитаты из найденных фрагментов.
`assistant.usp_GetRagTurn` отдаёт сохранённый ответ только пока все
использованные фрагменты и цитаты текущие и доступные. При отзыве доступа
HTTP возвращает `410` без текста ответа. Для POST хостингу нужен таймаут
больше 100 секунд; после обрыва процесса незавершённый ход может потребовать
ручного восстановления.

Подробные JSON-схемы, параметры и коды ответов находятся в OpenAPI. Полный
список реально зарегистрированных маршрутов и переменных окружения — в
[`backend/README.md`](../backend/README.md).
